# Moldova Labor Code RAG (RAG-система по Трудовому кодексу Молдовы)

Модульная Retrieval-Augmented Generation (RAG) система по законодательству Республики Молдова (Трудовой кодекс), реализованная на чистом Python без тяжелых фреймворков (LangChain / LlamaIndex).

## Стек технологий и архитектура

- **Язык**: Python 3.10+
- **Векторная БД**: ChromaDB (локальное хранилище)
- **Эмбеддинги**: Sentence-Transformers (мультиязычная модель `multilingual-e5-small` 384-dim по умолчанию / компактная `rubert-tiny2` 312-dim)
- **Reranker**: Cross-Encoder (`DiTy/cross-encoder-russian-msmarco`) / FlashRank (`ms-marco-MultiBERT-L-12`) / чистый dense-скор fallback
- **LLM**: Google Gemini Flash через официальный API (`gemini-3.5-flash-lite`, `gemini-3.8-flash`, `gemini-3.5-flash`) с лимитом от 2048 токенов
- **Архитектура**: Чистый модульный пайплайн с разделением ответственности:
  - `src/grabber/` — Сбор и дедупликация нормативных документов
  - `src/preprocessing/` — Парсинг HTML, очистка структуры и чанкинг по статьям
  - `src/embeddings/` — Векторизация и управление векторным индексом
  - `src/retrieval/` — Семантический поиск и фильтрация
  - `src/reranking/` — Переранжирование кандидатов
  - `src/generation/` — Формирование контекста и вызов LLM с защитой от галлюцинаций
  - `src/evaluation/` — Набор тестов и метрики качества (Hit Rate, MRR)

## Этап 1: Сбор данных (Grabber)

В рамках первого этапа реализован отказоустойчивый модуль автоматического сбора данных с государственного портала [legis.md](https://www.legis.md/):
- **Управление языковой сессией**: Автоматическая инициализация сессии через `https://www.legis.md/languages/index/ru` с сохранением cookie (`ci_session`) для получения актуального текста кодекса на русском языке.
- **Сборка полного документа**: Корректное объединение базовой разметки и динамически подгружаемого тела акта (`showdetails/{doc_id}`).
- **Стабилизация хеша**: Очистка динамических токенов Cloudflare (`__CF$cv$params`), гарантирующая детерминированный SHA-256 хеш.
- **Дедупликация**: Проверка SHA-256 по `data/raw/manifest.json`. Если нормативный акт не изменялся, повторное скачивание пропускается.
- **Метаданные**: Фиксация даты загрузки, URL и контрольной суммы в `metadata.json`.

## Этап 2: Предобработка и чанкинг данных (Preprocessing & Chunking)

В рамках второго этапа реализован модульный конвейер предварительной обработки и многостратегического чанкинга нормативного текста:

### 1. Очистка HTML (`src/preprocessing/cleaner.py`)
- **Извлечение контента**: Поиск основного контейнера документа (`div#contentdoc.doc`) с помощью `BeautifulSoup`.
- **Удаление служебных блоков**: Декомпозиция тегов `<script>`, `<style>`, `<button>`, `<form>`, `<nav>`, `<header>`, `<footer>`, `<iframe>` и элементов интерфейса (попапы, модалки, кнопки печати, логотипы).
- **Сохранение надстрочных индексов (`<sup>`)**: Преобразование тегов `<sup>` в формат `^{...}` (например, `Статья 7<sup>1</sup>` $\rightarrow$ `Статья 7^1`, пункты вида `b^1`), что исключает коллизии и склеивание статей с обычными номерами (например, исключает смешение статей `7^1` и `71`).
- **Нормализация символов**: Замена неразрывных пробелов `\xa0` и `\u200b` на стандартные пробелы, схлопывание множественных пробелов и нормализация избыточных переводов строк (`\n{3,}` $\rightarrow$ `\n\n`).

### 2. Синтаксический анализ структуры (`src/preprocessing/parser.py`)
- **Извлечение иерархии через RegEx**: Выделение разделов (`^РАЗДЕЛ\s+[IVXLCDM\d]+`), глав (`^Глава\s+[IVXLCDM\d]+`) и статей (`^Статья\s+\d+...`).
- **Склеивание многострочных заголовков**: Обработка переносов строк в заголовках статей и разделов, возникших при конвертации из Word в HTML.
- **Полнота извлечения**: Извлечены **14 разделов**, **66 глав** и **430 статей** кодекса без коллизий и потерь.
- **Атрибуты статьи**: Каждая статья содержит `number` (номер), `title` (заголовок), `text` (полный текст статьи), `body` (тело статьи без заголовка), `paragraphs` (список отдельных абзацев/пунктов), `section` (раздел) и `chapter` (глава).

### 3. Стратегии чанкинга (`src/preprocessing/chunker.py`)

Класс `TextChunker` реализует 4 стратегии разбиения текста:

| Стратегия | Параметры | Описание |
|---|---|---|
| **by_article** | — | Статья целиком является одним чанком. Основной рабочий набор для юридического RAG. |
| **fixed_size** | `chunk_size=500` | Нарезка текста статьи фиксированными блоками по 500 символов. |
| **fixed_overlap** | `chunk_size=500`, `overlap=100` | Нарезка блоками по 500 символов с нахлестом 100 символов (шаг 400 символов). |
| **by_paragraph** | — | Разбиение статьи по отдельным абзацам и пунктам (`paragraphs`). |

### 4. Структура метаданных чанка

Каждый чанк содержит уникальный детерминированный `chunk_id` и структурированные метаданные:

## Этап 3: Векторизация и Vector Database (Embeddings & Vector Indexing)

В рамках третьего этапа реализована подсистема векторизации и локального хранения векторных индексов нормативных документов на базе `Sentence-Transformers` и `ChromaDB`:

### 1. Обоснование выбора моделей эмбеддингов

В конфигурационном файле `configs/embeddings.json` моделью по умолчанию назначена мультиязычная модель **`multilingual-e5-small`**, на порядок лучше понимающая юридические синонимы, контекст и семантические соответствия (например, «отставка» $\leftrightarrow$ «увольнение по собственному желанию»):

| Модель / Алиас | HuggingFace Identifier | Размерность | Язык | Назначение и обоснование |
|---|---|---|---|---|
| **multilingual-e5-small** *(по умолчанию)* | `intfloat/multilingual-e5-small` | **384** | multilingual (100+ языков) | Высокоточная мультиязычная модель (~118M параметров, ~470 МБ). Понимает семантику синонимов и контекст. Автоматически использует асимметричный префикс `passage: ` при индексации документов и `query: ` при векторизации поисковых запросов. |
| **rubert-tiny2** | `cointegrated/rubert-tiny2` | **312** | ru | Компактная легковесная модель (~29M параметров, ~118 МБ). Поддерживается в качестве альтернативы для сверхбыстрого инференса на слабых CPU. |

- **Асимметричные префиксы E5**: Архитектура E5 требует префикса `query: ` для поисковых запросов и `passage: ` для индексируемых документов. Модуль `src/embeddings/embedder.py` автоматически добавляет префикс `passage: ` в методе `encode_documents()` и префикс `query: ` в методе `encode_query()`.
- **Инференс на CPU**: Принудительная инициализация с `device="cpu"` гарантирует полную переносимость и работу на любой рабочей станции без зависимости от дискретных видеокарт CUDA.
- **Нормализация векторов**: Все методы кодирования документов (`encode_documents`) и поисковых запросов (`encode_query`) используют `normalize_embeddings=True` ($L_2$-нормализация), что позволяет рассчитывать косинусное сходство через скалярное произведение, оптимизируя вычисления в HNSW.

### 2. Обоснование выбора ChromaDB

В качестве векторного хранилища выбрана **ChromaDB**:
- **Встраиваемая (Embedded) архитектура**: Работает напрямую в процессе Python через `chromadb.PersistentClient(path="chroma_db")` без необходимости запуска отдельных контейнеров Docker или сетевых сервисов.
- **Метрика расстояния Cosine**: Коллекции инициализируются с параметром `metadata={"hnsw:space": "cosine"}`, что строго соответствует $L_2$-нормализованным эмбеддингам.
- **Идемпотентность (`upsert`)**: Загрузка векторов выполняется через метод `upsert()`, гарантируя безопасный повторный запуск без риска дублирования чанков.
- **Локальная персистентность**: Все индексы и метаданные сохраняются в директорию `chroma_db/`.

## Этап 4: Поиск, фильтрация и реранкинг (Retriever, Filters & Reranker)

В рамках четвертого этапа реализован двухступенчатый поисковый конвейер (*two-stage retrieval pipeline*) с устранением узких мест моноязычных моделей и внедрением подробного диагностического режима.

### 1. Архитектура поискового конвейера

```text
[Поисковый запрос]
       │
       ▼
[VectorRetriever]  ──>  Векторизация (multilingual-e5-small, query: ...) + поиск в ChromaDB (Top-20)
       │
       ▼
[ContextFilter]    ──>  1. filter_by_min_length (>= 30 символов)
                   ──>  2. filter_by_threshold (similarity_score >= 0.50)
                   ──>  3. deduplicate_by_article (наиболее релевантный чанк на статью)
       │
       ▼
[DocumentReranker] ──>  Мультиязычный Cross-Encoder (DiTy Russian MS-MARCO / FlashRank MultiBERT / Dense Fallback)
       │
       ▼
[Финальный Top-5]   ──>  Отранжированный релевантный контекст с сохранением целевых статей
```

### 2. Векторный поиск Top-K (`src/retrieval/retriever.py`)

Класс `VectorRetriever` отвечает за быстрый первичный отбор кандидатов:
- **Подключение к ChromaDB**: Работает с актуальной коллекцией `chunks_by_article_multilingual-e5-small` (или любой выбранной моделью) через `chromadb.PersistentClient`.
- **Векторизация запроса**: Использует класс `EmbeddingModel` с автоматическим добавлением обязательного префикса `query: ` для модели E5 и $L_2$-нормализацией.
- **Расчет метрики сходства**: ChromaDB рассчитывает косинусное расстояние $d = 1 - \cos(\theta)$. Метод `retrieve()` возвращает `similarity_score = 1.0 - distance`.
- **Выходной формат**: Список словарей с ключами `id`, `text`, `metadata`, `distance`, `similarity_score`, отсортированный по убыванию сходства.

### 3. Фильтрация контекста (`src/retrieval/filters.py`)

Класс `ContextFilter` очищает пул кандидатов от нерелевантных, коротких и избыточных фрагментов:
1. **`filter_by_min_length(min_chars=30)`**: Удаляет артефакты разметки и обрывочные фрагменты короче 30 символов.
2. **`filter_by_threshold(threshold=0.50)`**: Отсекает семантический шум. Для модели E5 порог 0.50 надежно отсекает нерелевантные общие запросы и запросы вне предметной области.
3. **`deduplicate_by_article()`**: Устраняет дубликаты фрагментов одной и той же статьи кодекса, сохраняя чанк с максимальным баллом.
4. **`apply_all(config)`**: Последовательно применяет всю цепочку фильтров.

### 4. Мультиязычное переранжирование (`src/reranking/reranker.py`)

#### Устранение узких мест моноязычных реранкеров:
- **Проблема английской модели**: Англоязычные Cross-Encoder модели (такие как `ms-marco-MiniLM-L-12-v2`) ломали ранжирование русскоязычных правовых терминов, поднимая нерелевантные статьи (например, ст. 70 о командировках при вопросе об увольнении).
- **Мультиязычный Cross-Encoder**: Интегрирована русскоязычная модель `DiTy/cross-encoder-russian-msmarco` на базе RuBERT (~116 МБ). Модель тонко сопоставляет контекст запроса с текстом правовых норм на русском языке.
- **Поддержка FlashRank**: Реализована поддержка мультиязычной ONNX-модели `ms-marco-MultiBERT-L-12` с алиасом `ms-marco-Multi-MiniLM-L-12-v2`.
- **Режим чистого Dense Fallback**: Предусмотрен режим `"dense"` (сортировка по вектору схожести E5 без оверхеда на реранкер).

### 5. Диагностический режим (`src/retrieval/search_pipeline.py`)

1. **Детерминированность (`temperature: 0.0`)**: Исключает случайность генерации, гарантируя строгую воспроизводимость.

### 2. Математические формулы метрик (`src/evaluation/metrics.py`)

- **Hit Rate@K:**
  $$\text{Hit Rate}@K = \frac{1}{|Q|} \sum_{q \in Q} \mathbb{I}\left(\exists a \in \text{Target}(q) : \text{rank}(a) \le K\right)$$
  Возвращает 1.0, если хотя бы одна целевая статья присутствует среди первых $K$ документов выдачи, иначе 0.0. Средний Hit Rate@K по выборке отражает вероятность успешного нахождения релевантной нормы.

- **MRR (Mean Reciprocal Rank):**
  $$\text{MRR} = \frac{1}{|Q|} \sum_{q \in Q} \frac{1}{\text{rank}_1(q)}$$
  где $\text{rank}_1(q)$ — порядковый номер (ранг, начиная с 1) первого появления любой из целевых статей в списке выдачи (или 0.0, если целевая статья не найдена). Наказывает модель за низкое положение релевантного ответа в выдаче.

- **Precision@K и Recall@K:**
  $$\text{Precision}@K = \frac{|\text{Retrieved}_K \cap \text{Target}|}{K}, \quad \text{Recall}@K = \frac{|\text{Retrieved}_K \cap \text{Target}|}{|\text{Target}|}$$
  Оценивают концентрацию релевантных статей среди первых $K$ позиций и полноту охвата всех требуемых нормативных актов.

- **Hallucination / Refusal Rate:**
  Для $q \in Q_{\text{unanswerable}}$: проверка возврата стандартной фразы отказа («В предоставленном контексте информации недостаточно...»). Refusal Rate = 100% свидетельствует о нулевом уровне галлюцинаций (Hallucination Rate = 0%).

> **Анализ эффекта насыщения (Saturation Plateau) и динамики Recall:**
> 1. **Почему Hit Rate@K и MRR@K выходят на плато при $K \ge 3$:**
>    - Векторная модель `multilingual-e5-small` в связке с чанками по статьям (`by_article`) демонстрирует высокую плотность семантических представлений: для **25 из 26 запросов (96.2%)** хотя бы одна целевая статья обнаруживается уже на глубине $K \le 3$ (для 21 вопроса — на 1-м месте, для 3 вопросов — на 2-м месте, для 1 вопроса — на 3-м месте).
>    - Единственный запрос, не попавший в Top-3 (вопрос 21: *«условия прохождения испыталки»* из категории `synonym_slang`), имеет чрезмерно разговорную лексику и не попадает в выдачу даже при $K=20$.
>    - В результате метрика **Hit Rate** (факт наличия *хотя бы одного* попадания) и метрика **MRR** (обратный ранг *первого* вхождения) достигают потолка 96.2% и 0.8782 уже на $K=3$ и остаются константными при дальнейшем росте $K$.
> 2. **Почему ключевой растущей метрикой при $K > 3$ является Recall@K:**
>    - Метрика **Recall@K** оценивает долю извлечения *всех* целевых статей. В то время как Hit Rate остановился на 96.2%, **Recall@K монотонно возрастает**: $69.2\% \to 82.7\% \to 88.5\% \to \mathbf{92.3\%} \to \mathbf{94.2\%} \to \mathbf{96.2\%}$.
>    - Этот рост критически важен для категории **`multi_context`** (запросы, требующие синтеза 2–3 взаимосвязанных норм). На $K=3$ извлекается лишь первая статья, а дополнительные ключевые статьи (ст. 186 о выходных пособиях, ст. 158 о компенсациях за праздники, ст. 126 об отпуске по уходу) подтягиваются в контекст только на глубине $K=5$ и $K=10$.
> 3. **Компромисс с точностью (Precision-Recall Trade-off):**
>    - Полнота Recall@K увеличивается ценой размывания точности: Precision@K закономерно падает от 80.8% ($K=1$) до 22.3% ($K=5$) и 6.0% ($K=20$).
>    - **Вывод по выбору $K$:** Конфигурация **$K = 5$** является оптимальной рабочей точкой для LLM — она обеспечивает **Recall@5 = 92.3%** и **Hit Rate = 96.2%** при умеренном объеме нерелевантного контекста.

## Система мониторинга и телеметрии (Langfuse, Latency, Tokens, Cost)

В проект интегрирована подсистема комплексной наблюдаемости (*Observability*) на базе **Langfuse**, замера аппаратных задержек, гранулярного учета токенов и расчета оценочной стоимости генерации в режиме реального времени.

### 1. Архитектура спанов и трейсов

Для каждого пользовательского запроса формируется иерархический трейс, отражающий сквозной жизненный цикл выполнения в RAG:

```text
[Трейс Langfuse: rag_pipeline]
   │
   ├── 1. Спан [retrieval] (тип: retriever)
   │      ├── Входные данные: текст запроса пользователя
   │      ├── Выходные данные: список отобранных статей (ID, номер статьи, название, similarity_score, rerank_score)
   │      └── Метаданные: число кандидатов, время поиска и реранкинга (search_latency_ms)
   │
   └── 2. Спан [generation] (тип: generation)
          ├── Входные данные: системная инструкция + форматированный контекст статей
          ├── Выходные данные: сгенерированный ответ LLM
          ├── Модель: Gemini (например, gemini-3.5-flash-lite)
          ├── Usage Details: input (prompt) tokens, output (completion) tokens, total tokens
          ├── Cost Details: расчетная стоимость вызова в USD
          └── Метаданные: время генерации (llm_latency_ms)
```

### 2. Замер задержек и учет расхода токенов

- **Прецизионный замер задержек**: В `src/generation/rag_service.py` используется системный таймер `time.perf_counter()` для раздельного замера:
  - `search_latency`: время векторного поиска в ChromaDB, фильтрации и кросс-энкодер реранкинга.
  - `llm_latency`: время вызова и получения ответа от API Google Gemini.
  - `total_latency`: суммарное время сквозного обслуживания запроса.
- **Статистика токенов**: Модуль `src/generation/llm_client.py` извлекает данные напрямую из объекта `response.usage_metadata`:
  - `prompt_token_count`: токены промпта и поданного контекста нормативных статей.
  - `candidates_token_count`: токены сгенерированного юридического ответа.
  - `total_token_count`: суммарный объем токенов.
- **Расчет затрат (Cost Tracking)**: Метод `estimate_cost()` класса `TelemetryTracker` (`src/generation/telemetry.py`) автоматически рассчитывает стоимость по актуальным тарифам Google AI Studio для линейки Gemini Flash:
  - **Prompt (вход)**: $\$0.075$ за 1 000 000 токенов ($\$0.000000075$ / токен).
  - **Completion (выход)**: $\$0.30$ за 1 000 000 токенов ($\$0.00000030$ / токен).

### 3. Отказоустойчивый режим (No-Op Mode)

Если переменные `LANGFUSE_PUBLIC_KEY` и `LANGFUSE_SECRET_KEY` не заданы в файле `.env`, `TelemetryTracker` автоматически переключается в тихий локальный режим (*No-Op*):
- Работа системы и генерация ответов продолжаются без сбоев и сетевых задержек.
- Замер задержек, подсчет токенов и калькуляция стоимости производятся локально и выводятся пользователю.
- В поле ссылки на трейс выводится уведомление: `Langfuse Trace: Не настроен (No-Op mode)`.

### 4. Пример плашки метрик в консоли

При каждом запросе в CLI выводится структурированная плашка метрик:

```plaintext
[МЕТРИКИ ЗАПРОСА]:
• Задержка: 1.45 сек (Поиск: 0.15 сек | LLM: 1.30 сек)
• Токены: 1,340 (Контекст: 1,180 | Ответ: 160)
• Оценочная стоимость: $0.000137
• Langfuse Trace: https://cloud.langfuse.com/project/.../traces/...
```

## Входной Guardrail и Семантический кэш (Semantic Cache)

Для защиты от атак внедрения промптов (Prompt Injection), отсечения нецелевых запросов (Out-of-Domain) и ускорения типовых или синонимичных обращений реализован входной фильтр и SQLite семантический кэш, интегрированные в конвейер до поиска и вызова LLM.

```mermaid
graph TD
    UserQuery([Запрос пользователя]) --> FastSec{Prompt Injection?}
    FastSec -- "Обнаружена атака" --> BlockSec[Guardrail Block: Ошибка безопасности<br/>Latency < 1 мс | $0.00 | 0 tokens]
    FastSec -- "Безопасно" --> FastDom{Domain Check: ТК РМ?}
    FastDom -- "Вне домена" --> BlockDom[Guardrail Block: Отказ по домену<br/>Latency < 1 мс | $0.00 | 0 tokens]
    FastDom -- "Профильный вопрос" --> SC{Semantic Cache Lookup<br/>cosine similarity >= 0.92}
    SC -- "Hit (найден похожий)" --> CacheHit[Возврат из SQLite Cache<br/>Latency ~ 25 мс | $0.00 | 0 tokens]
    SC -- "Miss (новый вопрос)" --> RAGPipeline[SearchPipeline -> Gemini LLM]
    RAGPipeline --> SaveCache[Сохранение пары в SQLite]
    SaveCache --> FinalAns([Итоговый ответ и источники])
```

### 1. Архитектура входного Guardrail (`src/guardrails/domain_guard.py`)

- **Security Guard (Prompt Injection & Jailbreak)**:
  - Регулярные выражения и ключевые слова: перехватывает попытки обхода инструкций (`ignore previous instructions`, `забудь все инструкции`, `system prompt`, `ты теперь`, `act as`, `jailbreak`, `override`, `developer mode`).
  - Быстродействие: блокировка срабатывает на этапе лексического анализа за **< 0.1 мс**, предотвращая расход ресурсов CPU и токенов LLM.
- **Domain Guard (Гибридная проверка принадлежности к трудовому кодексу)**:
  - **Быстрый лексический слой**: проверка по корням ключевых терминов трудового права (`отпуск`, `увольнен`, `работ`, `договор`, `зарплат`, `труд`, `стаж`, `график`, `больничн`, `командировк`, `взыскан`, `профсоюз` и др.).
  - **Стоп-маркеры сторонних тематик**: отсечение кулинарии (`сварить`, `рецепт`, `зама`), астрономии (`космос`, `орбита`), уголовных преступлений (`кража`, `убийство`) за **< 1 мс**.
  - **Векторный семантический слой**: для сложных формулировок без явных ключевых слов вычисляется косинусное сходство с якорным вектором домена трудового права (`LABOR_DOMAIN_ANCHOR_TEXT`) и контрастным вектором нерелевантных тем. Порог семантического соответствия: `semantic_domain_threshold: 0.40`.

### 2. Архитектура Семантического кэша (`src/cache/semantic_cache.py`)

- **Хранилище**: локальная реляционная база данных SQLite (`data/cache/semantic_cache.db`).
- **Схема таблицы `semantic_cache`**:
  - `id` (INTEGER, Primary Key)
  - `query_text` (TEXT — оригинальный текст вопроса)
  - `embedding_blob` (BLOB — 384-мерный вектор эмбеддинга запроса `float32`)
  - `response_text` (TEXT — верифицированный ответ LLM)
  - `sources_json` (TEXT — список нормативных статей в JSON)
  - `created_at` (TIMESTAMP — время создания/последнего обращения)
  - `hit_count` (INTEGER — счетчик попаданий)
- **Алгоритм поиска**:
  - При поступлении нового запроса рассчитывается его векторное представление (L2-нормализованный вектор).
  - Вычисляется скалярное произведение (dot product / косинусное сходство) со всеми кэшированными векторами.
  - Если максимальное сходство $\ge 0.92$: фиксируется `Cache Hit`, инкрементируется `hit_count`, обновляется временная метка и ответ мгновенно возвращается без поиска по ChromaDB и вызова Gemini.
  - Если сходство $< 0.92$: фиксируется `Cache Miss`, запрос передается в стандартный конвейер RAG, а полученный ответ с источниками сохраняется в базу для последующих запросов.

### 3. Результаты валидационного тестирования (`src/guardrails/test_guard_cache.py`)

Проведено сквозное тестирование ключевых сценариев:

| # | Тестовый запрос | Ожидаемое поведение | Фактический статус | Задержка | Токены | Стоимость ($) | Экономия |
|---|---|---|---|---|---|---|---|
| **1** | *«Как сварить молдавскую заму?»* | Out-of-Domain блокировка | `GUARDRAIL_BLOCK` | **0.1 мс** | 0 | $0.000000 | **100%** |
| **2** | *«Какова продолжительность отпуска?»* | Первичный запрос (Miss) | `CACHE_MISS` | **9.85 сек** | 1,290 | $0.000124 | 0% (база) |
| **3** | *«Сколько дней длится отпуск?»* | Синонимичный парафраз (Hit) | `CACHE_HIT` (95.2% сходство) | **28 мс** | 0 | $0.000000 | **100%** |

3. **Наблюдаемость в реальном времени**: каждый статус (`guardrail_block`, `cache_hit`, `cache_miss`) логируется в Langfuse с соответствующими тегами и метаданными сходства.
